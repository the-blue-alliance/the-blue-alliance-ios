TBA for iOS ships several alternate app icons that users can switch between from **Settings → App Icon**. This page covers how they're wired up, how to add one, and the simulator bug you will almost certainly hit while testing.

## How Icons Are Wired Up

Icons live in [`the-blue-alliance-ios/AppIcons/`](https://github.com/the-blue-alliance/the-blue-alliance-ios/tree/main/the-blue-alliance-ios/AppIcons) as [Icon Composer](https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer) `.icon` bundles — the layered format introduced with the iOS 26 Liquid Glass icons. `AppIcon.icon` is the primary icon; everything else is an alternate.

Three things connect an icon to the app:

1. The `.icon` bundle is a member of the **Copy Bundle Resources** build phase.
2. Its name is listed in `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES` on the app target (space-separated), with `ASSETCATALOG_COMPILER_INCLUDE_ALL_APPICON_ASSETS = YES`.
3. A matching `<Name>Preview` image set exists in `Assets.xcassets/AppIconPreviews/` — see [Why the Preview Script Exists](#why-the-preview-script-exists).

`SettingsViewController` discovers icons at runtime by reading `CFBundleIcons` from the bundle, so **adding an icon requires no code changes**. Display names are derived from the icon name, so `ZachOrr` renders as "Zach Orr".

### Do Not Hand-Write `CFBundleAlternateIcons`

`actool` generates the entire `CFBundleIcons` dictionary — including `CFBundleAlternateIcons` — from `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES` at build time. Adding those keys to `Info.plist` by hand is redundant and will silently drift from the build settings.

To confirm what actually shipped, inspect the built app rather than the source `Info.plist` (right-click the product in Xcode's **Products** group → **Show in Finder** to locate it):

```
$ plutil -extract CFBundleIcons.CFBundleAlternateIcons raw -o - \
    "/path/to/The Blue Alliance.app/Info.plist"
```

## Adding an Icon

1. Design the icon in **Icon Composer** and save it as `the-blue-alliance-ios/AppIcons/<Name>.icon`.
2. Add it to the app target's **Copy Bundle Resources** phase.
3. Append `<Name>` to `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES` for both Debug and Release.
4. Build. The **Generate App Icon Previews** build phase creates the preview image set automatically.

If you skip step 3 the icon never registers as an alternate, and the App Icon section hides itself rather than showing a picker with nothing to pick — so a vanished section usually means a missing build setting.

Keep the lamp layer at the placement used by the other icons — `scale 6.27`, `translation-in-points [0, 0]` — which matches the official mark in [the-blue-alliance-logo](https://github.com/the-blue-alliance/the-blue-alliance-logo). Icons that disagree make the lamp visibly jump when switching.

Name image layers descriptively (`canopy-leaf-1.png`, not `leaf3 2.png`), and avoid spaces — Icon Composer will happily hand you filenames containing a narrow no-break space (U+202F), which is a cross-platform hazard.

Only ship art we have the rights to redistribute. Stock art pulled from an image search is not automatically usable.

## Why the Preview Script Exists

The Settings picker shows a thumbnail beside each icon. Getting that thumbnail is harder than it looks.

**Icon Composer icons cannot be loaded at runtime.** A `.icon` bundle has no raster representation — it compiles into layer data plus system-composed renditions inside `Assets.car`. Calling `UIImage(named: "Canopy")` does not return `nil`; it **throws** and crashes the app:

```
NSInternalInconsistencyException: 'Need an imageRef'
  -[_UIImageCGImageContent initWithCGImageSource:CGImage:scale:]
  -[_UIAssetManager imageNamed:configuration:]
```

There is no public API to render a `.icon` at runtime, so each icon ships a separate `<Name>Preview` image set that the picker uses instead. Those previews are generated by [`scripts/generate-app-icon-previews.sh`](https://github.com/the-blue-alliance/the-blue-alliance-ios/blob/main/scripts/generate-app-icon-previews.sh), which runs as the **Generate App Icon Previews** build phase.

The script compiles the icons with `actool`, then reads the composed renditions back out of the resulting `Assets.car` using `scripts/AppIconPreviewExtractor.m`. The extractor uses CoreUI, a private framework — this is acceptable because it is a **build-time developer tool that is never shipped in the app**, but it is the most likely part of this setup to break on a future Xcode release. If it fails, the build fails loudly rather than silently regressing previews.

Each preview ships **light and dark variants**, because the same icon can look completely different across appearances — the default icon is indigo-on-white in light and near-black in dark. `actool` has no public flag to emit an appearance-specific standalone render, which is the reason for reading `Assets.car` directly.

### Running It Manually

The script only re-renders icons whose preview is missing or older than the `.icon` bundle, so the no-op case costs well under a second.

```
$ ./scripts/generate-app-icon-previews.sh           # render what's stale
$ ./scripts/generate-app-icon-previews.sh --force   # re-render everything
$ ./scripts/generate-app-icon-previews.sh --check   # report staleness, write nothing
```

It also deletes previews whose `.icon` no longer exists, so removing an icon cannot leave orphaned art behind.

CI runs the **App icon previews** job on every pull request, which regenerates with `--force` and fails if the result differs from what's committed. It deliberately does not use `--check`: that compares modification times, and a fresh checkout gives every file the same timestamp, so it would always pass on a runner.

## Icon Switching Is Broken in the Simulator

**Alternate icon switching does not work reliably in the iOS 26 simulator.** The first switch after a fresh boot succeeds; every switch after that fails.

This is a simulator defect, not an app bug, and it is **not** caused by Icon Composer — a build from before the app adopted `.icon` bundles fails in exactly the same way.

### What Happens

`UIApplication.setAlternateIconName(_:completionHandler:)` is gated on the system first presenting the "You have changed the icon for…" confirmation alert. In the simulator runtime, the process that presents that alert — `CoreServicesUIAgent` — ships as a binary but has **no launchd job**, so it can never start. The result:

```
lsd: #ChangeIconWithAlert begin ... to Champs
lsd: #ChangeIconWithAlert couldn't make icon alert token:
     NSPOSIXErrorDomain Code=35 "Resource temporarily unavailable"
     -[LSIconAlertManager iconChangeAlertTokenForIdentity:error:]
```

The first attempt squeaks through with a spurious `Input/output error` and leaks the alert token. Every later attempt gets `EAGAIN` forever. The token lives in `lsd`, not in the app, so relaunching the app does not clear it.

Note that `alternateIconName` still updates and the completion handler can report success even when the icon does not visibly change — so the Settings checkmark may move while the Home Screen does not.

### Workaround

Restart the LaunchServices daemon to release the stuck token. This takes about two seconds, preserves installed apps and data, and buys exactly **one** more successful switch:

```
$ xcrun simctl spawn booted launchctl kickstart -k user/foreground/com.apple.lsd
```

`system/com.apple.lsd` works too, but `launchctl` warns that the identifier is deprecated.

Rebooting or erasing the simulator also works, but both are slower and gain you nothing extra.

### Test on a Device

Because of the above, **verify icon switching on real hardware** before shipping changes to it. Signing values are intentionally left empty in the project, so pass them at the command line rather than editing the project file:

```
$ xcodebuild -project the-blue-alliance-ios.xcodeproj -scheme "The Blue Alliance" \
    -configuration Debug -destination 'id=<device-udid>' -allowProvisioningUpdates \
    CODE_SIGN_STYLE=Automatic DEVELOPMENT_TEAM=<team-id> PROVISIONING_PROFILE_SPECIFIER="" \
    build
$ xcrun devicectl device install app --device <device-udid> \
    "<DerivedData>/Build/Products/Debug-iphoneos/The Blue Alliance.app"
```

Run `xcrun devicectl list devices` to find the device identifier.

## Home Screen Appearance Is a Separate Setting

If a preview in the picker does not match the Home Screen, check this before assuming a bug.

iOS has two independent appearance controls. App UI — including the picker — follows the **system** appearance. Home Screen icons follow the **Home Screen customization** setting (long-press the Home Screen → **Edit** → **Customize**), which offers Automatic, Light, Dark, and Tinted.

They agree only when that setting is **Automatic**, which is the default. If it is pinned to Light or Dark, the Home Screen icon will not match the picker preview, and there is no public API to detect it. An easy way to confirm: check whether Apple's own Calendar and Clock icons are rendering in the appearance you expect.

iOS also derives a **tinted** variant automatically. We do not supply one and cannot override it.
